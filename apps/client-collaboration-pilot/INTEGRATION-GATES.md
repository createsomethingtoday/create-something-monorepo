## Implemented locally

`identity-boundary.ts` calls the existing Canon `verifyIdentityToken`, not a decoded-claims stub. It requires ES256, exact issuer and audience, current Identity access-token kind/session version, verified email and at most 15-minute lifetime. Server-owned issuer/subject/tenant membership determines the role; token/body/header role and tenant claims are ignored. Returned principals are frozen and tracked privately; copying or forging the object fails domain authorization. Membership and expiry are checked again when the domain operation loads state.

Tests use ephemeral in-memory signing keys, synthetic subjects and a local JWKS response passed to the real Canon verifier. The optional HTTP boundary rejects unsigned/spoofed/expired/wrong-audience/nonmember callers, permits a verified reviewer, blocks a contributor's claimed reviewer role and immediately denies a revoked membership. It does not issue real credentials, fetch live JWKS, log in, create grants or alter accounts. The current port-4320 demonstration intentionally remains the existing synthetic-reviewer preview.

`deployment-version.mjs` maps the actual MaverickX content interfaces: page `/`, KV `content:home`, field `hero.title`, and the deployed source commit. Tests use recorded synthetic content shaped like that interface. Proposals/receipts bind Git source commit, exact repository bytes, deployment commit and exact KV JSON bytes. Old/missing/foreign evidence, source/runtime divergence and KV-only or deployment-only drift fail closed. Evidence must be no older than five minutes. Application rechecks the record immediately before Git ref CAS. A source-only commit leaves KV unchanged and the next source/runtime comparison is intentionally divergent until a separately authorized publisher reconciles it.

This is not an atomic live Git+KV transaction. A live deployment/KV writer can race after a remote read. Before hosted promotion, require a versioned content publishing protocol (ideally an immutable content manifest/version pointer with controlled writers), durable outbox and final deployment-version checks. An eventual-consistency KV read alone must not be described as a concurrency guarantee. No live reader/publisher is wired here.

## Cloudflare Artifacts candidate

Artifacts is a possible **proposal-workspace backend**, not a replacement for MaverickX's authoritative repository or its independently versioned KV content. Keep canonical source/Pages promotion unchanged. Reviewer decisions stay in the application judgment store (D1 for a hosted release); evidence/media can use R2. A proposal-workspace commit is not canonical source application or deployment approval.

`repository-port.ts` sketches the asynchronous boundary and explicitly identifies repository authority. The current implementation is local and synchronous: it assumes bare Git, local filesystem ownership, Git plumbing/private indexes, `update-ref` CAS, and reachable commit-message receipts. It has no GitHub-specific API/account assumption. A remote adapter needs asynchronous intent/outbox coordination instead of holding a SQLite transaction across network writes.

Verified research relayed by the parent: [Artifacts changelog](https://developers.cloudflare.com/artifacts/platform/changelog/) describes open beta; [Git protocol](https://developers.cloudflare.com/artifacts/api/git-protocol/) provides HTTPS Git operations; [Workers binding](https://developers.cloudflare.com/artifacts/api/workers-binding/) provides repository lifecycle/read operations. No conditional-ref REST create-commit or built-in reviewer approval was established. Implement remote writes through documented Git protocol only after verifying expected-ref/lease semantics. Do not invent a REST CAS endpoint.

[Build-on-push documentation](https://developers.cloudflare.com/artifacts/guides/build-and-deploy-on-push/) concerns Workers; no direct Pages integration for `maverick-x` was verified. [Pricing](https://developers.cloudflare.com/artifacts/platform/pricing/) requires a separate access/budget decision; no hard monetary cap was established. No Artifacts repository, fork, token, binding or service was provisioned.

Before implementing the remote adapter, test: two simultaneous pushes against one expected ref (one must fail), tenant/repository-scoped token denial, token expiry/revocation, disconnected-after-push reconciliation, immutable commit readback, forged/tampered receipt detection, quota exhaustion, no automatic retry amplification, and Git+KV drift at canonical promotion. If conditional update semantics or bounded costs cannot be demonstrated, leave remote application disabled.

Any later Artifacts access approval must name the existing account/namespace, one private synthetic proposal repository, its retention/operation budget and the exact short-lived repository token scopes. It must separately authorize provisioning and token issuance. It should not authorize canonical-repository migration, Workers/Pages deployment, broad namespace credentials or live client-data upload by implication.
