# MCP Registry Workflow

How to edit the CREATE SOMETHING MCP registry, what each command does, and why
the registry is split into two source layers.

If you are looking for higher-level context, start with
[`docs/MCP_HUB_CONTROL_PLANE.md`](../MCP_HUB_CONTROL_PLANE.md). This guide is
the contributor-facing workflow doc.

## TL;DR

| What you're doing | File to edit |
|---|---|
| Add or remove a CREATE SOMETHING / WORKWAY / agency MCP | `config/mcp-hub/registry.core.json` |
| Change a hand-curated bundle (e.g. `core`, `ops`, `slack`, `local-dev`) | `config/mcp-hub/registry.core.json` |
| Change `defaults` (enabled bundles, codex config path) | `config/mcp-hub/registry.core.json` |
| Toggle an MCP enabled/disabled at runtime | `config/mcp-hub/state.json` |
| Update tenant routing / alias failover | `config/mcp-hub/routing.json` |
| Update the JSON schema | `config/mcp-hub/registry.schema.json` |
| **Never edit by hand** | `config/mcp-hub/registry.json`, `config/mcp-hub/registry.composio.generated.json` |

After any edit, run:

```bash
pnpm mcp:registry:generate
pnpm mcp:registry:validate
pnpm mcp:registry:check
pnpm mcp:registry:coverage
pnpm mcp:registry:test
```

The husky pre-commit hook runs `mcp:registry:validate` automatically when you
stage any of the registry source files.

## Layer model

The registry is split into two source files plus a deterministic merge step.
This was done in CRE-267 because the previous flat `registry.json` was 96%
machine-generated Composio noise hiding 46 hand-curated entries; reviewers
could not see signal through the noise.

```
config/mcp-hub/registry.core.json                (hand-authored)
  + 46 servers (CREATE SOMETHING + WORKWAY + agency)
  + 17 hand-curated bundles
  + defaults

config/mcp-hub/registry.composio.generated.json  (overwritten by nightly sync)
  + 984 composio-toolkit-* servers
  + 89 composio-all and composio-category-* bundles

config/mcp-hub/registry.json                     (generated by merge)
  = merge(core, composio)
  = the flat view every consumer reads at runtime
```

Invariants enforced by `pnpm mcp:registry:validate`:

1. Servers prefixed `composio-toolkit-` live only in the composio layer.
2. Bundles named `composio-all` or prefixed `composio-category-` live only in the composio layer.
3. `defaults` lives only in the core layer.
4. No key collisions between layers.
5. `registry.json` matches `merge(core, composio)` (the drift check in
   `pnpm mcp:registry:check` fails otherwise).

## Commands

```bash
# Validate the layers (schema + policy + state.json refs + name policy + invariants).
pnpm mcp:registry:validate

# Rebuild registry.json from the two layers and regenerate the playbook
# catalog + fleet doc. Run this after any source edit.
pnpm mcp:registry:generate

# Verify the generated artifacts match what would be regenerated. Used by CI.
pnpm mcp:registry:check

# Cross-check that every MCP package on disk is classified in PACKAGE_COVERAGE
# and that every fleet deployment URL/wrangler config exists.
pnpm mcp:registry:coverage

# Run the validator unit tests.
pnpm mcp:registry:test

# One-time bootstrap (already executed; only useful if rebuilding the split).
pnpm mcp:registry:split

# Rebuild registry.json from the layers without regenerating the playbook
# catalog or fleet doc. `generate` is usually what you want.
pnpm mcp:registry:merge

# Refresh nightly composio toolkit inventory from the Composio API. Writes to
# the composio source layer, then mcp:composio:sync-and-generate chains the
# merge step to rebuild registry.json.
pnpm mcp:composio:sync
pnpm mcp:composio:sync-and-generate
```

## How to add a new MCP

1. Add the server entry under `servers` in `config/mcp-hub/registry.core.json`.

   ```jsonc
   "my-new-mcp": {
     "transport": "http",
     "url": "https://my-new.mcp.createsomething.agency/mcp",
     "description": "What this MCP does in one line.",
     "tags": ["domain", "owner", "cs"],
     "bearer_token_env_var": "MY_NEW_MCP_API_TOKEN",
     "catalog_exposure_mode": "direct",
     "estimated_tool_count": 5
   }
   ```

2. Add the new server name to any bundle it belongs to (e.g. `bundles.ops`).

3. If the MCP has a Cloudflare Worker package, add an entry to `PACKAGE_COVERAGE`
   in `scripts/mcp-registry-coverage.mjs` so the coverage gate knows about it.

4. Run:

   ```bash
   pnpm mcp:registry:generate
   pnpm mcp:registry:validate
   pnpm mcp:registry:coverage
   ```

5. Commit `registry.core.json`, the regenerated `registry.json`, the regenerated
   `docs/MCP_FLEET_REGISTRY.generated.md`, the regenerated playbook catalog,
   and (if applicable) `scripts/mcp-registry-coverage.mjs`.

## Naming policy

Hand-authored server names must match `^[a-z][a-z0-9-]*$` (kebab-case
alphanumeric, leading letter). Composio toolkit names (`composio-toolkit-*`)
are exempt because the slug suffix comes from an upstream provider and may
contain underscores.

If a rename is impossible and a sunset plan is documented, add the name to
`GRANDFATHERED_SERVER_NAMES` in `scripts/mcp-registry.ts`. The grandfather
list is intentionally empty at HEAD; reintroductions require explicit review.

## Exposure policy

See [`docs/MCP_CATALOG_EXPOSURE_POLICY.md`](../MCP_CATALOG_EXPOSURE_POLICY.md)
for the full text. The validator enforces three thresholds:

| Tool count | Allowed `catalog_exposure_mode` |
|---|---|
| 0 – 25 | `direct` |
| 26 – 75 | `direct` only with documented `exposure_exception_reason` and `exposure_review_owner` |
| 76+ | `brokered` or `exception_direct` (with reason + owner) |

Broad connector surfaces (e.g. anything tagged `toolkit` plus `composio`) are
automatically classified `brokered` at 100+ tools.

## How the nightly composio sync interacts with the layers

1. `.github/workflows/composio-registry-sync.yml` runs nightly at 04:17 UTC.
2. `scripts/composio-registry-sync.ts` calls the Composio API, normalizes the
   toolkit list, and **overwrites only `registry.composio.generated.json`**.
   The core layer is never touched by the sync.
3. `pnpm mcp:registry:generate` (chained via `mcp:composio:sync-and-generate`)
   rebuilds the merged `registry.json`, the playbook catalog, and the fleet
   doc from both layers.
4. `pnpm mcp:registry:check` verifies the merge is deterministic and the
   generated artifacts are up to date.
5. The workflow opens a PR (`codex/composio-registry-sync`) containing the
   diff. Human review on that PR is the production-promotion gate.

If the composio API returns zero toolkits (or otherwise fails), the sync
script refuses to overwrite the file so a partial outage cannot delete the
toolkit catalog.

## PR-time gating

`.github/workflows/mcp-registry-check.yml` runs on any PR that touches:

- `config/mcp-hub/**`
- `packages/**/package.json`
- `packages/cs-mcp-hub/**`
- generated artifacts
- `scripts/mcp-registry.ts` / `scripts/mcp-registry-coverage.mjs` /
  `scripts/composio-registry-sync.ts` / `scripts/test/mcp-registry.test.mjs`

It runs validate → check → coverage → test. A failing PR cannot merge into
`main` until the source layers, the merged registry, and the generated
artifacts are mutually consistent.

## Common errors and what to do

| Error | Why | Fix |
|---|---|---|
| `Registry artifacts are out of date: ... registry.json` | You edited `registry.core.json` (or the composio layer) but forgot to regenerate. | Run `pnpm mcp:registry:generate` and commit the result. |
| `Registry artifacts are out of date: ... catalog.registry.generated.ts` or `MCP_FLEET_REGISTRY.generated.md` | Same as above. | Same: regenerate and commit. |
| `server <name>: present in both core and composio layers` | You added a `composio-toolkit-*` server by hand to the core layer (or vice versa). | Move it to the correct layer; layers must not overlap. |
| `bundle <name>: present in both core and composio layers` | Same as above for bundles. | Same: move to the correct layer. |
| `<file>: defaults must live in the core layer` | A `defaults` block was added to the composio layer. | Move it to `registry.core.json`. |
| `server <name>: server names must be kebab-case` | New entry uses `_` or other non-kebab characters. | Rename. Composio toolkit names are exempt; do not abuse this. |
| `server <name>: direct catalog exposure is not allowed for estimated_tool_count >= 75` | A large surface is marked `direct`. | Switch to `brokered`, or to `exception_direct` with `exposure_exception_reason` + `exposure_review_owner`. |
| `state.json: enabledServers references unknown server: <name>` | A server was renamed/removed from the registry but `state.json` still references it. | Update `state.json` to use the new name or drop the stale reference. |
| `manifest <path> is not referenced by config/dify/inventory.json` (from `pnpm dify:inventory:generate`) | A Dify agent manifest was added but no corresponding agent entry was registered. | Either register the agent in `config/dify/inventory.json`, or set the manifest's `status` to a draft value (`draft_pending_studio_import`, `draft`, or `planned`) if the agent is not yet live. |
