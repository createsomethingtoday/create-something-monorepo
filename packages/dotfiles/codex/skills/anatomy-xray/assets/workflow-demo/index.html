READ THE BOUNDARY

Declaration ≠ enforcement.

A prose.md contract describes what should happen. Host permissions and tool checks determine what can happen. Verification checks what did happen. A receipt records the evidence; it does not make that evidence correct.

XRay: ghosted enclosure, overlapping assemblies and rear-routed paths. Selected assembly and adjacent handoffs emphasized.

Text equivalent & evidence map

The numbered route is Intent → Contract → Orchestration → Host gate → Tools → Verification → Receipt. A denied or pending required approval stops before tools. Failed or unknown verification returns to repair or escalation. These exception paths are described here, not simulated by the drawing.

AssemblyRole & limitationEvidence
1. IntentA person defines the desired result, scope, and constraints. Unclear intent needs clarification before consequential work.task · schematic
2. ContractA prose.md file can declare inputs, outputs, acceptance criteria, and policy. Text alone does not enforce those limits.task · schematic
3. OrchestrationA coordinator chooses steps, passes context, and handles failures. This illustrative sequence is not a universal runtime architecture.framework · schematic
4. Host gateThe host applies permissions and approval rules. A required approval may be denied or pending; either stops the gated action. Tool servers may enforce additional limits.task · schematic
5. ToolsAuthorized calls read or change resources. A successful response must still be checked against the intended result. No tools run in this demo.framework · schematic
6. VerificationCompare resulting state with acceptance criteria and authoritative evidence. Failed or unknown checks require repair or escalation, not a success claim.charter · schematic
7. ReceiptRecord intent, authority, source, action, verification, and recovery. A receipt is not automatic proof; evidence can be incomplete or wrong.charter · schematic
