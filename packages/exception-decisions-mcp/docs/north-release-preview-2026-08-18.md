## Requires fixes before resubmission
- **Published checkout failed and concealed its error** — In our test the published checkout never loaded — just an endless spinner — and the code logged "success" after the failure. a buyer stares at a blank box with no idea anything went wrong, and the merchant never finds out either.
  Fix: implement explicit loading/success/failure states, stop loading after failure, expose a recoverable error, never emit success from a failed operation; demonstrate the complete ordinary-user installation and published checkout path.
- **React Router must be updated (published security advisories)** — The app ships a routing library version that has published security advisories. We didn't find a working exploit in how it's used — the fix is a routine version bump and rebuild. known-vulnerable versions in a payments app are an easy, checkable no.
  Fix: update react-router and react-router-dom to 7.18.2 or later, include the complete package manifest and lockfile, rebuild the production artifact, run a dependency audit, and retest all routing and authentication flows.
- **Published North scripts omit required integrity attributes (SRI)** — All six published scripts load with no integrity fingerprint, so if North's server ever served altered code, customer sites would run it without noticing. the fingerprint is the browser's only way to refuse tampered code.
  Fix: register every external script with an immutable versioned URL and valid integrity hash, then provide the registration responses and final rendered tags; dynamic loaders are not a substitute for pinning the complete runtime.
- **Published navigation accepts unsafe schemes and unrestricted destinations** — Buttons send visitors to whatever address is typed into an attribute — including script-executing links and look-alike external sites — with no check before the redirect. on a payment page, an unchecked redirect is how people end up typing card details into a fake site.
  Fix: require a same-origin relative checkout path or enforce HTTPS with an explicit declared-host allowlist immediately before navigation.
- **Webflow identity token transmitted through a GET URL** — The token that proves who the Webflow user is gets sent as part of a web address. addresses end up in server logs, browser history, and analytics — places a login credential must never sit.
  Fix: change the route to POST and send the token in a protected request body or authorization header; keep it out of query strings, redirects, responses, logs, and analytics.
- **Credentialed CORS accepts arbitrary website origins** — North's payment servers currently answer authenticated requests from any website on the internet, not just North's and Webflow's. a malicious site could ride a logged-in user's credentials straight into the payment API.
  Fix: exact HTTPS origin allowlist of required North and Webflow origins only; reject all others; keep authentication and tenant authorization independent from CORS.
- **North scripts injected on pages without a checkout** — The checkout scripts load on pages that have no checkout — the style guide, even the 404 page. code should only run where its feature lives; anything more widens the blast radius of every other issue on this list.
  Fix: apply each script only to pages containing its declared functionality and provide the exact registered and applied Custom Code records showing placement.
- **Checkout quantity is client-controlled and not safely validated** — The quantity field accepts nonsense — negative numbers, hex values, numbers too large to count reliably — and we saw nothing on the server that re-checks the math. totals, inventory, and what a customer is actually charged all hang off a number a shopper can garble.
  Fix: require a finite safe integer within explicit min/max in the browser; independently derive and validate product ownership, inventory, unit price, taxes, fees, quantity limits, and final total on the server.
- **Custom Code removal and uninstall handling are incomplete** — Deleting a checkout cleans up almost everything except the scripts themselves — they stay on the customer's published site after the customer thinks the app is gone. "uninstalled" has to mean uninstalled; leftover third-party code on a live site is a liability the customer doesn't know they have.
  Fix: implement and demonstrate the complete register/apply/update/remove/disconnect/uninstall/republish lifecycle while preserving unrelated customer scripts.
- **Opening the Extension silently creates and adopts site resources** — Just opening the app adds 70 styles and 9 variables to the customer's site before they've clicked anything — and when a name already exists, the app takes over the customer's own resource and may later edit or delete it. apps shouldn't touch a site until asked, and should never delete something the customer made.
  Fix: create resources only after explicit user action, track durable ownership identifiers instead of names, and remove only resources North can prove it created.
- **App Marketplace long description requires a production-ready rewrite** — The store listing still reads like an internal draft — staging labels, unsupported claims, and wording that implies Webflow runs the product. the listing is the merchant's basis for trusting a payments app with their revenue; it has to say plainly what the app does, costs, and requires.
  Fix: rewrite in clear English covering actual functionality, the North-hosted payment surface, requested permissions, merchant onboarding and underwriting, processing and other fees, supported countries and currencies, conditional Apple Pay/Google Pay/ACH eligibility, Webflow plan and custom-domain requirements, customer data handling, script installation/removal behavior, and North support channels; remove internal review labels, "North Staging App", unrelated revenue-sharing content, and undemonstrable claims.
- **Debug merchant identity assignment included in the production bundle** — The shipped app still contains developer shortcuts that assign which merchant account gets paid — including a hidden settings page where the browser can submit a merchant ID directly. who receives the money must be decided by the server from the logged-in user, never by whatever the browser claims.
  Fix: remove all debug merchant routes, prefill calls, and bypass flags from the production artifact; derive merchant association server-side from the authenticated, authorized Webflow user/site; prevent clients from assigning merchant identities; provide the backend for review; rebuild and retest the exact production bundle.
- **Review package is incomplete and contains production residue** — The review package is just the compiled output — no source project, no build files, no server code — and it still identifies itself as the dev build. for a payments app we have to be able to rebuild and inspect exactly what ships, and right now we can't.
  Fix: provide complete reproducible client and backend sources with exact lockfiles, tests, migrations, and build instructions; remove development identity and CLI state.
- **Reviewed script loads mutable, undeclared executable code (dynamic second-stage + fingerprinting + native overrides)** — The script we reviewed quietly loads a second, unreviewed script from North's server, which pulls in a third library that fingerprints the visitor's browser and rewrites built-in browser functions. whatever we approve today isn't what runs tomorrow, and shoppers are being fingerprinted without anyone disclosing it.
  Fix: submit every executable dependency with immutable versioned URLs and integrity hashes; remove dynamic second-stage loading, undisclosed fingerprinting, and native-function overrides.
- **Published runtime is not safe to initialize more than once** — Running the scripts twice stacks them — in our test, one click on "+" jumped the quantity from 1 to 3. script updates on live sites routinely load alongside old versions; the code has to survive that without double-charging behavior.
  Fix: make initialization idempotent, mark initialized roots, reuse owned resources, prevent duplicate listeners, and ensure Custom Code updates replace prior versions.
- **Merchant onboarding documentation is missing** — There's no guide for the merchant sign-up process — how underwriting works, how long approval takes, what fees apply, or how to pick up a half-finished application. merchants hit underwriting on day one; without documentation, every confused merchant becomes a support ticket for Webflow.
  Fix: add step-by-step guidance covering account creation, required business/identity information, underwriting requirements, expected review timing, supported countries and business types, approval/rejection states, production activation, Webflow plan or custom-domain prerequisites, processing fees, payment-method eligibility, resuming an incomplete application, onboarding data handling, and support; documentation must match the actual customer flow demonstrated during review and distinguish test, pending, approved, and production-ready states.
- **Editable IDs inserted into CSS selectors without escaping** — A single stray quote or bracket in a product ID crashes the script and breaks every quantity picker after it on the page. one malformed product silently disables purchasing for the rest.
  Fix: enforce the expected product-ID format, use CSS.escape(), and handle malformed items without stopping all initialization.
- **Payment messages do not validate their sender** — The checkout accepts "payment complete" messages without checking who sent them. any other script on the page could tell the store a payment succeeded when it didn't.
  Fix: validate the exact expected North origin, iframe window, and message schema on every message; do not redirect, fulfill, or release value until the server verifies authoritative payment status.
- **Preview Hider is incompatible with an enforced CSP** — On security-strict sites, the script that hides the placeholder card form can be blocked — leaving what looks like a payment form sitting visible on the page. the fallback state of a payment UI can't be "exposed fake card form."
  Fix: remove runtime style injection and configure visibility through the approved installation flow or another reviewed CSP-compatible mechanism; do not require unsafe-inline.
- **Server-side payment and tenant controls cannot be reviewed** — The browser tells North's servers what product, quantity, and price to charge, and we received no server code showing anyone double-checks it. we can't verify that a shopper can't simply name their own price — or that orders, refunds, and merchant payouts are protected at all.
  Fix: provide a complete buildable backend snapshot matching production and demonstrate user, site, merchant, product, price, inventory, webhook, replay-protection, fulfillment, and deletion controls.
