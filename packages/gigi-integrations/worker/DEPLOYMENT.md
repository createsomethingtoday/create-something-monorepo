# GiGi connector promotion contract

This Worker is not live merely because the desktop companion builds. The D1 migration is applied; production promotion still requires an independent review of the Identity resource policy, secret binding, deployment, and an end-to-end owner readback. Do not reuse or broaden the existing shared Gmail auth config.

The dedicated Composio v3.1 `POST /api/v3.1/auth_configs` body for Gmail is:

```json
{"toolkit":{"slug":"gmail"},"auth_config":{"type":"use_composio_managed_auth","name":"GiGi beta Gmail read-only","credentials":{"scopes":"https://www.googleapis.com/auth/gmail.readonly"}}}
```

The dedicated body for Google Calendar is:

```json
{"toolkit":{"slug":"googlecalendar"},"auth_config":{"type":"use_composio_managed_auth","name":"GiGi beta Calendar read-only","credentials":{"scopes":"https://www.googleapis.com/auth/calendar.events.readonly,https://www.googleapis.com/auth/calendar.calendars.readonly"}}}
```

Composio documents [v3.1 auth config creation](https://docs.composio.dev/reference/api-reference/auth-configs/postAuthConfigs) and [comma-separated scope overrides for managed OAuth](https://docs.composio.dev/docs/authentication/controlling-scopes). On 2026-09-30, the shared developer project was checked for existing GiGi configs; there were none. Dedicated Gmail `ac_s2YEkh21bMT8` and Google Calendar `ac_zHJSY3Mbuv-q` were created. Independent GET readback returned HTTP 200 for each, `ENABLED`, Composio-managed `OAUTH2`, the correct toolkit, and the exact read-only scopes above. No user connection was created or read. If Google/Composio later adds required scopes, stop for review rather than silently expanding the Worker allowlist. A new user's consent and `connected_accounts/{id}` readback must show the exact same auth config, derived user ID, `ACTIVE`, `PRIVATE`, and approved scopes before any source page is exposed.

The Worker origin is exactly `https://gigi-connector.createsomething.workers.dev`; Identity's protected resource and desktop OAuth audience must equal that origin. `GIGI_ALLOWED_SUBJECTS` is a server-only comma-separated list of individually approved Identity subjects. Do not use a global allow-any policy. The dedicated D1 consent database `gigi-connector-consent` has ID `bcefe77e-d4b7-4d70-9002-1f969eef3457`, bound as `DB` in `wrangler.toml`; migration `0001_connections.sql` was applied remotely on 2026-09-30 and a `PRAGMA table_info` readback confirmed the `reconnectable` column. The journal then contained zero connection attempts. `COMPOSIO_API_KEY` is also a server-only secret; never put it in the desktop bundle or a Wrangler variable. `wrangler.toml` contains the exact reviewed auth config IDs and scope strings. `wrangler deploy --dry-run` parsed and bundled it with the correct D1 binding on 2026-09-30; it did not deploy. `/health` returns HTTP 503 `unconfigured` until all bindings and the beta allowlist are available, so an incomplete Worker cannot appear healthy.

The unauthenticated connection callback only displays a static return-to-app message. It grants no connection. The authenticated reconcile route must independently verify provider ownership. A unique D1 index allows one outstanding or active attempt per subject/provider; uncertain provider POSTs require readback, not a new request ID. Status readback moves a previously linked or active account to `attention` only when Composio returns the exact same owner, auth config, toolkit, and scopes with a terminal `FAILED`, `EXPIRED`, `INACTIVE`, or `REVOKED` status. This releases the guard for fresh consent. Network errors, account mismatches, and ambiguous states leave the guard intact. Source pages remain bounded and read-only. The desktop must persist their projected records to its local SQLite database and confirm saved IDs; the Worker stores only consent metadata.

For a `dispatched` attempt whose provider POST or D1 update outcome was unknown, status performs a bounded Composio v3.1 connected-account list using the derived owner ID and exact auth config. It requires a complete page, one matching alias equal to the request ID, a creation time consistent with the attempt, and then an independent exact-account GET. It binds only an `ACTIVE`, pending, or terminal account that still matches the owner, toolkit, private account type, and scopes. A pending account without its original hosted consent URL returns `attention` with `recovery: operator_review`; it never fabricates a URL. A zero-match or ambiguous attempt stays guarded; after ten minutes its status also reports operator review. No status path retries the link POST.

Operator recovery is a deliberate exception, not a timer-based automatic release. For a zero-match attempt, read the exact subject, provider, request ID, and creation time from D1. At least 24 hours after the attempt, perform a complete Composio account-list read filtered by that subject's derived user ID and the dedicated auth config; repeat the same read at least ten minutes later. Require `next_cursor: null` on both reads and prove that neither list contains the alias equal to the request ID or any account attributable to this attempt. Re-read D1 immediately before the write and require the same row to remain `dispatched` with `connected_account_id IS NULL`. Only then may an authorized operator conditionally change that row to `attention` with `reconnectable=1`, accepting exactly one changed row. Log the operator, time, reason, exact owner/config/alias filters, both complete-list receipts, the pre-write D1 readback, and the conditional-write receipt. Do not retry the provider POST or issue a blind SQL release. If an account exists but lacks a usable consent URL, do not release by age; wait for a provider terminal status or have the operator resolve that account in Composio, then use the broker's terminal readback path. Any incomplete page, account mismatch, nonterminal provider state, concurrent row change, or uncertain operator write remains blocked for manual investigation. This recovery has not yet been exercised with a real consent attempt.

Promotion evidence should include: reviewed Identity resource policy; Composio auth-config readback for both dedicated configs; D1 migration applied; Worker deployment ID and `/health` readback; user PKCE sign-in; real Gmail and Calendar consent; owner-bound active account readback; one source page imported and deduplicated locally; and independent mobile-to-desktop acceptance. The local automated suite and synthetic official CTX import/search do not establish those live results.
