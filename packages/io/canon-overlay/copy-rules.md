# IO Research Artifact Overlay Copy Rules

Use this file to define IO-local research artifact language while preserving Canon structure.

## Rules

- Name the workflow object before the action.
- Name the owner, evidence, receipt, and next action when a surface asks for trust.
- Keep state words stable across modalities: `ready`, `review`, `blocked`, `complete`.
- Keep reasoning and policy details off thin displays; summarize the decision and route to the full receipt.
- Do not rename Canon primitives to project-specific concepts when the primitive behavior is unchanged.
- Start research claims with the artifact, source, status, proof, and next reading/action.
- Keep paper-specific argument, speculation, visual language, and publication posture local to IO content files.
- Use Canon terms for structure: `proof`, `receipt`, `artifact`, `policy`, `overlay`, and `extension intake`.

## Voice And Chat

- Prefer short declarative sentences.
- Make handoffs explicit: who owns the next step, what proof exists, and where the durable record lives.
- Do not put private chain-of-thought, hidden policy text, or speculative rationale in user-visible output.
- Summarize research as claim, source artifact, proof, and next action.
- For voice, do not read long paper sections. Point to the paper route, catalog entry, or visual summary.
- For chat, prefer file-backed metadata before rendered copy.

## Web And App

- Put proof beside claims.
- Use action labels that describe the result, not the component.
- Keep local marketing tone in project copy files, not Canon primitives.
- Web papers can carry full research narrative and citations.
- App surfaces should keep artifact status, visual proof, review state, and next action scannable.
- Do not promote one paper's structure into Canon until repeated research surfaces need the same template.
