# Duplicate finder lifecycle safeguards

This class has no active namespace binding in the current package configuration. Before wiring it into a Worker, explicitly choose positive safe integers for `DUPLICATE_SCAN_MAX_PAGES` (maximum unique Notion pages retained per job) and `DUPLICATE_SCAN_MAX_DURATION_MS` (total wall-clock deadline, including archival). No business allowance is selected in code. Missing/invalid limits reject `/start` with 503; preexisting jobs lacking limits stop durably instead of continuing unbounded. Existing start payload/status response fields are retained.

Only one pending/running job is admitted per object; concurrent starts return 409. A new completed/cancelled-job replacement clears accumulated pages. Pagination rejects empty, missing, repeated and cycling cursors and responses without new pages; page count and deadline are durable. Each provider call is bounded by the remaining deadline and a 30-second network timeout. Alarm work is limited to five provider calls, with checkpoints and rate spacing between calls.

Cancellation aborts the current request and prevents late results from overwriting terminal state or rearming an alarm. Already accepted provider writes cannot be recalled. An interrupted/failed archive has uncertain provider outcome: the job fails and requires reconciliation before starting another scan; there is no blind mutation retry. An interruption with a persisted in-flight query likewise stops conservatively. Successfully checkpointed archive progress resumes without repeating known completed requests. Access tokens are cleared from terminal job state, and provider error response bodies are not persisted.

Run `pnpm --filter @create-something/notion-agent test:cost-guards`. All provider responses are local fakes. Remaining decisions: choose the two job limits, authenticate/authorize the eventual caller and database identity, and select an account-level admission quota before exposing this currently unbound class. Per-object limits do not restrict many fresh object IDs. A staging Workers-runtime alarm/eviction test remains required before deployment. Rolling back to old code removes these bounds; stop job admission and reconcile outstanding provider writes first.

An independent 96 KiB serialized-state ceiling prevents oversized accumulated pages or job data from repeatedly failing storage writes. Exceeding it is a terminal error requiring narrower database scope. This technical ceiling may stop a scan before its configured page budget; it preserves bounded storage rather than silently dropping results.
