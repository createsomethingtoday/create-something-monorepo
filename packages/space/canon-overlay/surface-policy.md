# Space Workbench Overlay Surface Policy

This policy keeps @create-something/space overlays portable across web, chat, app, voice, glasses without forking Canon.

## Web

- Use Canon components and tokens first.
- Add project-local layout, copy, and theme aliases only when the consuming route needs them.
- Keep receipt, evidence, and owner metadata visible near decisions.
- Route families: `/`, `/playground`, `/praxis`, `/motion`, `/data`, `/discover`, and API-backed tool routes.
- Full live controls, datasets, playgrounds, and detailed receipts belong on web routes.

## Chat

- Return compact summaries grounded in overlay artifacts.
- Name the registry item or template before suggesting a local primitive.
- Route primitive changes through Canon extension intake.
- Prefer structured routing, experiment, and data artifacts before inferred summaries.
- Answer with tool, state, required input, proof, and next action.

## App

- Preserve touch targets, focus order, and text state labels.
- Use local templates for workflow-specific screens, not new base components.
- Keep tool state, owner, input, proof, and next action visible beside controls.
- Use app surfaces for operator review, data inspection, and workflow receipts.

## Voice

- Speak status, owner, and next action.
- Do not read long policy text. Point to the receipt or durable record.
- Summarize workbench handoffs as tool, state, owner, proof, and next action.
- Do not read large datasets, route lists, or control descriptions.

## Glasses

- Show only glanceable state, owner, and next action.
- Keep reasoning, review history, and policy bodies on larger surfaces.
- Show tool status, owner, next action, and receipt only; keep controls and datasets on web/app.

## Promotion Boundary

Project overlays can become Canon candidates only after repeated-surface evidence exists. Until then, keep implementation, copy, and policy local to the named overlay.
For Space, promote the reusable workbench structure only. Keep experiments, datasets, playground details, and production-affecting actions local to the owning workflow.
