# AI-Native Review Phase 1 Subset

**Status:** Draft
**Date:** 2026-05-26
**Parent spec:** `ai-native-review-standardization-spec.md`
**Rubric map:** `rubric-codification-map.md`

## Goal

Start with a small, deterministic review subset that can produce reliable findings from published HTML, CSS, JS, asset metadata, and browser runtime measurements. Do not attempt full visual-quality scoring or autonomous final decisions in Phase 1.

Phase 1 should answer:

- Is there a clear hard blocker?
- Are there objective changes a reviewer can trust quickly?
- Is the submission likely average/iterative rather than clean good?
- Which manual checks remain before approval, rejection, or exceptional review?

The official grading rubric should be used as the quality-band source. The local submission-guidelines draft should be used for concrete pass/fail requirements.

## Explicit Non-Goals

- No final approval or rejection.
- No feature/exceptional decision.
- No full plagiarism/flooding enforcement.
- No subjective visual taste score.
- No broad Dify exposure until evals show the subset is stable.

## Small Subset Scope

Run read-only analysis on 25-50 recent template submissions across these groups:

- approved good
- approved exceptional
- rejected low quality
- changes requested / response to review
- duplicate or same-design examples when available

The sample should include multiple reviewers, but reviewer identity is calibration context only.

## Phase 1 Evidence Sources

### Published HTML

Use for:

- headings and H1 count
- placeholder/lorem/default Webflow text
- links and utility-page discoverability
- image alt attributes
- forms and labels
- Webflow runtime markers
- obvious script/embed policy signals
- semantic section/page structure

### CSS

Use for:

- CSS variables and token adoption
- line-height units
- hover/focus state presence
- excessive fixed heights or overflow patterns
- breakpoint/media-query coverage
- repeated or autogenerated class naming signals
- color declarations for contrast sampling

CSS can reveal quality patterns, but many are proxies. Treat them as quality signals, not final design judgments.

### JS

Use for:

- legacy IX2 markers
- unsupported external scripts
- risky globals or OAuth/security patterns
- framework/library detection
- excessive or unusual custom code
- animation/plugin policy checks

JS findings can be deterministic when the rule is explicit. Broader "too much custom behavior" should remain partial unless tied to a specific policy rule.

### Asset Metadata

Use for:

- extreme file sizes
- missing or unsupported image formats
- repeated asset usage
- suspicious asset names
- broken asset loads

Asset licensing, trademark, and visual suitability remain manual or partial until the similarity/licensing system is mature.

### Browser Runtime Measurements

Use Playwright/E2B-style browser runs for deterministic measurements:

- horizontal overflow at fixed viewport widths
- clipped or offscreen important text
- visible 404/broken pages
- form field accessibility attributes
- interactive states that exist in DOM/CSS
- console errors and failed network requests
- basic layout shift or viewport coverage observations

## Screenshot Policy

Screenshots should be evidence artifacts, not the scoring engine.

Use screenshots for:

- human verification
- before/after comparison
- attached evidence for findings
- deterministic visual measurements derived from the page runtime

Avoid using screenshots alone for:

- "good design"
- "modern"
- "premium"
- "cohesive"
- "exceptional"

Screenshot-based computer vision can be added later as a partial signal, but Phase 1 should not let it drive rejection or exceptional labels by itself.

## Phase 1 Recommendation Labels

Use these internal labels:

- `hard_blocker_candidate`
- `changes_requested_average`
- `clean_good_candidate`
- `manual_quality_review_required`

These are safer than immediately exposing `likely_rejected`, `average`, `good`, and `exceptional_candidate` to reviewers. The public four-band language can be introduced after calibration.

## Initial Rule Families

### Hard Blocker Candidates

- legacy IX2 detected after policy cutoff
- site inaccessible or major crawl failure
- severe custom-code/security-risk signal
- forbidden external scripts or app connections when detectable
- exact duplicate/same-design submission when strong evidence exists

### Objective Change Candidates

- missing required utility page or required utility link
- missing noindex on required utility page
- invalid homepage SEO title format
- multiple or missing H1s
- skipped heading levels
- missing image alt attributes
- unlabeled form fields
- broken internal links
- placeholder/default Webflow text
- extreme oversized assets
- horizontal overflow on standard viewports
- PageSpeed/Lighthouse score capture when available
- unique link-name and CTA-route extraction

### Quality Proxy Signals

These should inform reviewer focus, not final outcome:

- weak breakpoint coverage
- overuse of fixed dimensions
- missing hover/focus states
- poor class naming hygiene
- low CSS variable/token adoption
- limited layout variety across pages
- repeated section structure
- weak CTA distribution
- unusually high script or asset weight
- type-scale inconsistency
- limited hover/focus state coverage

## Evals Before Reviewer Exposure

Before exposing any new Dify reviewer-facing action, evaluate:

- false positives on approved good/exceptional examples
- missed hard blockers on rejected examples
- whether approved rows with historical requested changes are interpreted correctly
- reviewer disagreement cases
- stability across repeated runs on the same URL

Minimum bar for Phase 1:

- hard-blocker candidates have near-zero false positives
- objective findings include direct evidence and page URLs
- every manual gap is explicitly labeled
- no recommendation is presented as an official decision

## Calibration Note: 2026-05-26 Expanded Sample

The first 25-record calibration run in `phase1-expanded-calibration-audit-2026-05-26.md` produced too many unresolved mismatches for reviewer-facing ratings:

- 3 false hard blockers, all driven by current published-site IX2 evidence against approved Good outcomes.
- 4 missed blockers, mostly guideline or invalid-submission outcomes outside the current published-site evidence surface.
- 7 data-ambiguous cases where the current public site or available outcome fields are not enough to decide whether the agent, reviewer, policy, or historical snapshot is responsible.

The IX2-gated rerun cleared the hard-blocker false positives by keeping `wf.template.code.no_legacy_ix2` as evidence plus `ix2_policy_confirmation`, not as an automatic hard-blocker recommendation. The updated counts were:

- 0 false hard blockers.
- 5 aligned cases.
- 10 acceptable-caution cases.
- 6 data-ambiguous cases.
- 4 manual-quality gaps after normalizing `Other` rejection feedback.
- 0 hard-blocker misses after app/guideline and manual-quality gaps were separated from deterministic Phase 1 misses.

Until the IX2 policy question is answered and separate manual-quality plus app/guideline data-surface lanes exist, Phase 1 remains an offline calibration and evidence-normalization workflow.

The most important manual-quality lane is visual quality. `visual-quality-signal-standardization.md` should be treated as the source for outdated/basic visual-style normalization. The agent may report these as `manual_quality_review_required` with sub-buckets and proxy evidence, but Phase 1 should not auto-reject on visual taste. `visual-quality-proxy-canary-audit-2026-05-26.md` confirms why: the first 30-URL proxy canary detected signals on all rejected visual-quality cases, but still produced medium proxy load on 26.7% of approved controls.

The stability mechanism for this lane is `visual-quality-self-healing-loop.md`: rolling golden sets, reviewer-language aliases, drift events, and policy proposals. This loop can make the visual-quality signal more reliable at scale, but only through versioned policy snapshots and human-approved promotions.

## Build Order

1. Add `rule-catalog.phase1.json`.
2. Add D1 review ledger tables behind a non-reviewer-facing worker path.
3. Normalize current agent-controlled validator output into Phase 1 findings.
4. Add browser runtime measurements for horizontal overflow and clipped content.
5. Store screenshots and raw outputs in R2.
6. Backfill the 25-50 record evaluation sample.
7. Compare against Airtable outcomes and reviewer overrides.
8. Introduce coordinator-plus-lane orchestration from `review-orchestration-model.md`.
9. Only then design reviewer-facing tool language.
